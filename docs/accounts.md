# Accounts, logins and keeping data apart

One **account per aviary**. An account has team members (the Staff / Volunteer people on the My Team screen); every record in
the database belongs to exactly one account, and a request can only ever see its own account's rows.

## How the separation works
- `sql/038_multi_tenant.sql` adds an `account_id` to every record table, puts it in each primary key (so two accounts can use the
  same ids), and turns on **row-level security**: a policy on every table says "only rows whose account_id equals
  `app.account_id`". The policy is forced even for the table owner.
- Each API request (`api/_lib/db.js`) opens its own database connection, switches to the low-privilege role `birdbox_app`, and
  sets `app.account_id` (and `app.auth_id`). From then on Postgres filters every query — handlers don't have to remember to.
  An account id that isn't set means no rows and failed inserts, never "all rows".
- `api/_lib/auth.js` turns a request into a login (`authId`, `email`). `auth_links` maps a login to its account.
- Photos and PDFs can't send a login header, so file URLs carry a short-lived signature (`api/_lib/signing.js`).
- **Use the direct Neon connection string** (host without `-pooler`) for `DATABASE_URL`; the code refuses the pooled one, because
  a pooled backend could carry one request's account setting into another's.

## Turning logins on (Neon Auth / Stack Auth)
1. Run `sql/038_multi_tenant.sql`, then `sql/039_demo_data.sql` (needs the species table loaded: `npm run seed:species`).
   Until 038 is run the app behaves exactly as before (one account, no logins).
2. In `js/auth-config.js`, define `window.BirdBoxAuth` (instructions are in that file).
3. Vercel environment: `AUTH_MODE=stack`, `STACK_PROJECT_ID=<your Neon Auth project id>`, and — once — `LEGACY_OWNER_EMAIL=<the email
   you will sign in with>`. That login adopts everything that existed before accounts (account id `legacy`); everyone else gets a
   brand-new account on first sign-in. (If your token's JWKS lives somewhere else, set `STACK_JWKS_URL`.)
4. Deploy. Signed-out visitors see a sign-in screen; the first sign-in creates the account (an Owner team member, an aviary, and a
   copy of the sample aviary).

`AUTH_MODE=test` (accepts `x-test-auth-id` headers or a `test:<id>:<email>` token) is for automated tests only — never set it in
production.

## Sample data
The sample aviary lives in the `demo` account (`sql/039_demo_data.sql`, generated by `scripts/gen-demo-account.js` — edit the
script and regenerate). New accounts get a copy, flagged `is_demo`; **Settings → Your account** has *Remove sample data* (deletes
only the flagged rows) and *Load sample data*. The demo account itself is never readable from normal requests.

## Adding a new table later
End its SQL file with `select bb_make_tenant('table_name', 'primary_key_column(s)');` — that adds `account_id`, the composite
primary key, the policies and the grants. If it should be part of the sample data, add it to `DEMO_TABLES` in
`api/account/index.js` and to the generator script. The older optional seed scripts (020, 021, 026, 027) predate accounts and
are superseded by 039.

## Not built yet
- **Team logins / invites:** adding a team member doesn't yet let them sign in; the plan is an invite by email that links their
  login to the same account with their role. Permissions per role come after that.
- Per-account customisation of menus is stored per account already; sharing an aviary between two accounts is not supported.
- Pooler-safe mode (a transaction per request) if the direct connection ever becomes a limit.
